# 业务类型与投影统一内容定义

正式规格及后续决策见 [#108](https://github.com/hansonyu183/zerp-ui/issues/108)，承接 [ADR-0001](0001-library-owned-page-layout.md) 的页面与布局所有权。

后续目标修订见 [ADR-0004](0004-reactive-business-model.md) 与 [#122](https://github.com/hansonyu183/zerp-ui/issues/122)：业务结构、数据和操作统一为响应式模型，对象成员直接表达层级，取消消费者页面组装；纯 model 子入口不依赖 Vue 及消费者业务职责边界继续保留。新模型由 #123–#125 实施；0.31.1 的历史发行仍采用下文契约。

整合 oit-go 新客户模块时，采用一份业务类型及有序列表/表单投影作为统一内容定义入口，由库生成嵌套字段、对象分区和集合结构；本次迁移的页面消除重复字段描述。取舍是消费者需要迁移定义，换取字段含义和列表、表单内容的一致性。

既有表单、CRUD 和写入恢复运行时继续承担交互生命周期，扩展树形引用、秘密值的保留/修改/清除以及独立关联资源，不复制客户页面内的另一套运行时。通用模型同时服务前后端，通过无 Vue、Vuetify 和 CSS 依赖的公开 `@zerp/ui/model` 子入口提供，与 UI 同包同版本发布，避免引入独立包的版本协调成本。客户具体定义、业务规则、权限计算、API、Session 和 Router 仍由消费者持有。

库保证各写入运行时的未知结果锁和原请求恢复；跨独立资源的业务联锁由消费者的业务规则及权威权限事实决定。页面离开保护可以汇总所属运行时的未决状态，但不因此推导兄弟资源的写入权限，不固化“同一客户下全部禁写”等业务策略。

本决定不恢复暂停的纯 API 驱动方案 #106，不改变仅经 AuthPage/AppPage 呈现完整页面的边界。本记录只表达已确认取舍，不代表实现、发布或真实应用接入已经完成。
