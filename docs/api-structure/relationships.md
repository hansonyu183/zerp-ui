# 关联、横向扩展、纵向属性与单据聚合的 UI 整合

本补充是目标 API 及 UI 推导规范的一部分，仍然只做设计。物理表关系由 OIT 适配；UI 只处理业务引用、闭合对象与有归属的集合。不能根据表名后缀、字段 `_id` 后缀、某条数据样本或 SQL 表结构猜业务关系。

## 一、记录里的关联字段

以 `eba.emp_id → app_emp.emp_id` 为例。当前依据是 `master-data/party-references.ts`；员工名称取 `app_emp.name`，停用资格按原规则。目标客户对象的 employee 字段是业务引用，而不是裸编号文本。

| 操作 | API 与数据 | 库内交互 |
|---|---|---|
| 列表读取 | 服务器批量解析 `{id,name,resource}`，字段Schema及candidate关系在空列表也存在 | 单元格显示名称，编号作为辅助信息；不会每行再发员工查询 |
| 详情读取 | 名称和业务id一起返回，resource是API业务身份 | 可读的引用以正常链接打开关联记录，支持新标签；无目标读取资格时不提供打开动作 |
| 编辑 | 当前写Schema只允许 `ReferenceKey={id}`；名称不可写。候选关系给出明确员工资源与约束 | 一个引用选择输入，按名称/编号检索、分页、选定和清空；不把id/name/resource拆成三个文本框 |
| 已选值回填 | 候选接口支持同一资格下按id解析；停用历史值通过单独读取资格解析 | 原值显示并标明停用；不得作为新选择，允许保留与否由当前动作Schema/业务校验确定 |
| 级联引用 | 例如省依赖国家；依赖关系通过字段candidate资源描述及草稿返回值体现 | 上级变化提交草稿计算，服务器返回下级新Schema和有效值，不由UI私自保留过期下级 |

不能把“能看到客户的业务员名称”等同于“能读取员工全部资料”。允许返回的引用名称本身受源字段资格校验；目标员工详情另行鉴权。若只允许看编号，输出该次字段Schema中没有name且不提供打开关系；若连编号也无权，字段整体不返回。不存在、已停用、无权、已删除历史引用必须由服务器提供有限业务状态/诊断，UI不能凭404补出名称。

候选列表与已选解析都不能绕过行级范围；输入只提交id，服务器重查名称/状态并重验选择资格。当前账套、身份、父行、依赖或活动性变化使旧候选响应和选择事件失效。

## 二、一对一横表与纵向属性

物理横表是同一业务对象的一组固定字段；纵表是按属性定义存储的字段值。它们都不天然成为独立导航、独立列表或任意键值编辑器。

目标客户聚合示意：

```json
{
  "id": "C1",
  "base": {"name": "合成客户", "employee": {"id": "E1", "name": "合成员工", "resource": "employees"}},
  "extensions": {"billing": {"bill_day": "25", "pay_type": "A", "ex_price": "1.0000"}},
  "attributes": {"priority": "A", "visit_date": "2026-11-09"}
}
```

这只是合成的Schema快照：实际bill_day/pay_type枚举来自现有字典，priority/visit_date是假定已定义的合成属性，不能把这两项加入生产业务定义。

| 存储 | 目标结构 | 展示、编辑及提交 |
|---|---|---|
| `eba` 固定列 | `base`闭合对象 | 主要事实与常用字段；编辑采用当前动作写Schema |
| `eba_ext` 一对一固定扩展 | `extensions.billing`闭合对象，title为“账款设置” | 同一客户详情中的业务区块；拥有单独资格/动作时库呈现局部管理动作，该动作有独立草稿/提案/回执，不能借普通客户保存越权修改 |
| `eba_attr(eba_id,attr_id,attr_val)` | `attributes`闭合properties，每个属性id独立类型、title、required及候选关系 | 少量属性自动成Form字段，多行说明自动多行文本；不展示数据库attr_id/attr_val通用表。属性定义管理仍是独立业务资源 |
| 扩展字段与属性重名 | 层级命名空间保留，不摊平覆盖 | 错误路径、资格、脏值、预览均使用JSON Pointer，例如`/extensions/billing/bill_day`、`/attributes/priority` |

当前 `customer-settings.ts` 实际输入还包含 `pay_type/tran_type/cd_type/ex_price/hk_price/fd_price/fee_price/owe_limit`；`owe_limit`映射eba额度，其他设置映射eba_ext。其资格是原管理员/role_5/role_6规则，固定扩展行缺失当前返回409。目标保留该规则：读取可表示扩展不存在，禁止伪造默认行自动插入；显示业务阻断原因，只有另有明确获权创建动作时才可创建。

`attributes`的字段集合由app_attr_def和当前资格生成；Schema在值为空时仍完整。已有属性默认值只在原业务允许的初始化/创建时应用；读取缺行不自动落库。null表示显式清值，字段缺席表示当前动作未覆盖/保持，不等同删除。历史异常但本次未修改的值，保持现有“未触碰则保留”规则；变更后必须按当前定义校验。不新增客户端条件表达式。

横表扩展的一对一由资源归属和唯一键保证，纵表属性按owner+attr_id唯一；转换由后端负责。`additionalProperties:false`用于最终有效输入，不能把不同类型的属性塞进一个string/number联合字典。未知/未登记属性不得自动变成输入字段。

## 三、主记录、业务头、主明细、子明细及各层扩展

当前实际层次为：`ebs_v` 通用单据主记录，`ebs_vr` 物料业务头，`ebs_vr_item`同时承载is_main=Y的主产品行与非main行。头纵属性是`ebs_v_attr`，行纵属性是`ebs_vr_item_attr`；还有内嵌ext_1..8/vr_item_ext_1..6及账套注册的专用横表，例如ebs_v_ext_ba、ebs_vr_item_ba_ext、ba_attr、ba_item_attr。仅登记表名并不证明当前服务可写该表；这些专用表必须逐项注册业务投影和资格后才可提供写动作，不能自动全表开放。

目标物料单据为固定有限层次，**不增加递归Form Schema**：

```text
单据聚合（唯一root id、revision和依赖基线）
├─ header.common       ebs_v中的通用业务字段
├─ header.business     ebs_vr中的物料头字段
├─ header.extensions   已登记的一对一头横扩展，按业务对象分组
├─ header.attributes   通用头/业务头的已定义纵属性，命名空间防冲突
├─ mainLines[]         主产品行，各有稳定rowKey
│  ├─ values / extensions / attributes
│  └─ children[]       该主行归属的非main子行
│     └─ values / extensions / attributes
└─ independentLines[]  业务允许的无主行非main行，不强塞给第一条main
   └─ values / extensions / attributes
```

每一层Schema明确字段、对象、数组、主键及候选关系；库无需知道表名。头、主行、子行、独立行的可写字段可以不同，分别绑定动作/行的有效Schema；不能用一个通用“明细字段字典”套所有层。

`main_id`在当前初始化/BOM/重算路径中有分组键和行号使用差异，后端必须以对应单据领域规则归一成稳定parent rowKey，不能假定`main_id=item_id`。历史不一致不能由UI静默挂靠、丢行或修复；以可读原始事实及诊断展示，禁用受影响操作。排序使用服务器权威业务顺序，不能依据当前数组序号生成持久主键。

### 库内固定展示规则

- 主记录和业务头位于详情/编辑上部，标识、状态、创建审核等事实只读；对象区块用业务title作为分组，横表不另开导航。
- 桌面主明细显示表格；可展开当前主行的子明细表。当前行的横扩展、纵属性和较长文本在行详情区集中查看/编辑，不将所有扩展列硬塞到同一宽表。
- 没有主从层次的独立行显示单独明细集合，不伪造主行。手机使用记录卡片及分层展开，保持父子归属、操作状态和错误定位。
- 普通属性字段采用该层有效Schema生成控件；计算字段/合计只读。主行和子行按各自候选范围选择产品、单位、仓库/库位，禁止复用另一行过期候选。
- 切换活动主行/子行不提交最终业务写入；本地脏值属于root草稿及稳定rowKey。库负责固定交互和Vuetify主题，不从API读取组件、布局、展开模板或任意render。

### 编辑和事务

新增行先请求root草稿下对应collection的行初始化，客户端rowKey用UUID，服务器回传值、有效Schema和版本；BOM/来源生成和数量价格联动都由草稿计算返回。禁止根据已有第一行复制结构或自动从样本猜列。保存整份值只能改变当前获权、已载入的字段，不把未加载/无权字段或子集合当空值删除。

行删除是显式的草稿行操作，不以省略一个数组元素猜测删除意图。删除主行预览列出有权可见的受影响子行与业务结果；如存在不能随动作处理的依赖则禁用，不暴露隐藏子项数据。子行重挂、手工增删、数量覆盖、BOM刷新只在当前类型业务允许时出现；不能因UI有拖动能力就开放重挂。

整个单据聚合一次Proposal冻结主、头、所有允许变更行及每层横纵扩展、来源、库存/财务和脚本依赖基线，在既有事务边界原子提交。普通客户字段与需要单独客户设置授权的扩展可以是不同动作/事务边界；边界由后端业务动作持有，UI不自行把多个保存接口拼成“保存成功”。非事务外部effect保持逐项证据。

头/行扩展并发修改、属性定义变更、来源变化、权限变化都冲突失效；不能只比较ebs_v时间戳。错误用稳定rowKey和字段Pointer定位，重排序不把错误挂到另一行。unknown锁属于原root动作；折叠区块、切行、切页、重读某行均不能解除。committed后刷新任意局部失败仅重读，不重发单据。

## 验收矩阵

| 合成设计场景 | 期望 |
|---|---|
| 客户列表100条共用同一员工 | 服务器批量解析，无100次逐行请求；名称与id同时保留 |
| 编辑业务员，无员工详情读取资格 | 可选当前获权候选；无越权详情链接；不能写name |
| eba_ext无行/无设置权限 | 不自动创建；分别体现业务阻断/没有操作资格 |
| attr无值、历史异常、定义改版 | 完整字段Schema；未改旧值保留；已改值重验；提案版本冲突 |
| 同名属性出现在头、主行、子行 | namespace+rowKey准确定位，互不覆盖 |
| main及非main与独立行并存 | 后端归一parent；UI不按main_id数值擅自挂靠 |
| 子行只读、扩展字段隐藏、主行可写 | 各层独立有效Schema/资格；root提交不能越权 |
| 删除主行、BOM重算、未知结果与迟到响应 | 显式草稿操作、服务端计算、权威核对、scope隔离 |

上述是规范的合成验收要求，不是已执行UI或真实数据库验收。
